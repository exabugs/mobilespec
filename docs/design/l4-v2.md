# L4 v2 設計案（2.0）

- ステータス: **提案中（レビュー待ち。実装はこの文書の承認後）**
- 対象: L4（状態・データ契約）の書式、検証、移行コマンド `mobilespec migrate`
- 関連: [01_principles.md](../01_principles.md)、[02_structure_model.md](../02_structure_model.md)、[LLM_SPEC.md](../LLM_SPEC.md)

## 1. 背景: 実運用で何が起きているか

実運用のプロジェクト（モバイルアプリ、L4 が 29 ファイル、イベント 90 件）を集計した。

| 観点                                                                             | 結果                                                                                             |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `data.queries` / `data.mutations`（OpenAPI の `operationId` への接続）を使う画面 | **0**                                                                                            |
| データの取得元を、散文の文字列で書いたファイル（例: `'API: GET /venues/{id}'`）  | 14（HTTP パスの言及 42 か所）                                                                    |
| `callQuery` / `callMutation` イベント                                            | **0** 件。API 呼び出しは `update` イベントの `description` に散文で書かれる（`update` は 29 件） |
| `state` の書式                                                                   | すべて「名前 → 説明文字列」（型なし）。別の書式（`stateData`、型付きのリスト）も混在             |
| `conditions`                                                                     | 59 件中、式に見えるのは 13 件。残りは散文                                                        |
| 画面イベントの種類                                                               | navigate 57 / update 29 / navigateStack 2 / updateState 1 / external 1                           |

**mobilespec の中核である「縦の接続」**

```text
L3.action → L2.transition.id → L4.events → L4.data(query/mutation) → OpenAPI.operationId
```

**は、L4 → OpenAPI の手前で途切れている。** URL・HTTP メソッドを直書きしない、という原則（[01_principles.md](../01_principles.md)）が、自由記述の文字列の中で破られている。構造的に書く道はあるが、書きにくいため使われなかった。

### 原因（推測を含む）

1. `state` / `conditions` が「説明文字列」で足りてしまい、型・式を書く動機がない。検証もされない
2. API の呼び出しは、`callMutation` で書くより、`update` の `description` に書くほうが楽
3. クエリの引数（パスパラメータなど）や結果を、状態・条件から参照する手段がない。構造にしても、使い道がない
4. 画面のパラメータ（`params`）を宣言する場所がない

## 2. 目標と非目標

### 目標

- 構造的に書くほうが、散文で書くより**楽**で、**検証の見返りがある**
- L4 から OpenAPI の `operationId` までの接続を、実際に成立させる（引数の整合まで検証する）
- 状態・条件・パラメータに型を与え、AI が型付きで実装を生成できるようにする
- 既存の仕様を**失わずに**移行できる（`migrate` が散文を保持し、変換できないものは TODO として残す）
- 1.x の利用者が、段階的に移行できる

### 非目標

- 任意のプログラムの記述（制御構文、関数の定義）。L4 は契約であって、実装ではない
- UI のレイアウト（L3 の責務）
- 実行時のランタイムの提供

---

## 3. 全体方針: ファイル単位の `version: 2`

L4 の各ファイルの先頭に `version: 2` を書くと、v2 として検証する。無いファイルは v1（従来どおり）。

```yaml
version: 2
screen:
  id: item_detail
  ...
```

- **v1 の挙動は凍結する。** 2.x では v1 を受け付け、`info` で「v2 へ移行できる」と出す。v1 の削除は 3.0
- 厳しい検査（§6）は **v2 のファイルにだけ**適用する。これで、2.0 を入れても、既存の仕様が突然壊れることはない
- `migrate` は v1 → v2 を変換する（§7）。プロジェクトの都合の良いタイミングで、ファイルごとに移行できる

> 「2.0」にする理由: v2 では、書式が互換でなくなり（`state` のリスト化など）、検査が厳しくなるため。ただし、v1 が使い続けられるので、利用者の CI が一斉に壊れることはない。

## 4. L4 v2 の構造

### 4.1 全体像

```yaml
version: 2
screen:
  id: item_detail
  context: ... # 従来どおり
  description: 画面の説明（人間向け）

  params: # 画面に渡されるパラメータ（遷移の params の受け口）
    - name: id
      type: string
      required: true
      description: 項目の ID

  sources: # API 以外のデータ源（端末のセンサー、永続化された設定など）
    location:
      kind: device
      type: { latitude: number, longitude: number }
      description: 端末の位置

  data: # OpenAPI に接続するデータ
    queries:
      item:
        operationId: getItem
        args: { id: $params.id } # OpenAPI の引数を、params / state / 他の query から与える
        selectRoot: data # 従来どおり（応答のどこを使うか）
      isMember:
        operationId: getMyMembership
        args: { id: $params.id }
    mutations:
      join:
        operationId: joinItem
        args: { id: $params.id }
        options: { idempotent: true, retry: 2 } # 従来の mutationOptions

  state: # 画面ローカルの状態（型付き）
    - name: activeTab
      type: string
      enum: [info, members]
      default: info
    - name: draft
      type: { title: string, body: string? } # オブジェクト型。? は省略可

  conditions: # 式で書く。散文は description に
    isLoading:
      expr: item.isPending
      description: 取得中
    canJoin:
      expr: '!isMember.data && !item.isPending'
      description: メンバーでなく、取得が終わっているとき

  events:
    action_join: # L3 の action / L2 の transition.id と一致
      type: callMutation
      mutation: join
      guard: canJoin
      onSuccess:
        refetch: [isMember]
        set: { activeTab: members }
    action_open_members:
      type: navigate
      targetScreenId: item_members
      params: { id: $params.id }
```

### 4.2 型（`type`）

| 書き方                              | 意味                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| `string` / `number` / `boolean`     | プリミティブ。`enum:` で値を列挙できる                                                            |
| `{ a: string, b: number? }`         | オブジェクト。`?` は省略可                                                                        |
| `[string]`                          | 配列（要素の型）                                                                                  |
| `$ref: '#/components/schemas/Item'` | OpenAPI のスキーマ（`openapi.path` が必要）。クエリの結果の型にも使う                             |
| `unknown`                           | 型が未定義。**info** で報告（`migrate` が、型を決められなかったものに付ける。段階的な移行のため） |

query / mutation の結果の型は、OpenAPI の応答スキーマ（`selectRoot` を適用した後）から決まる。宣言は不要。

### 4.3 式（`expr`）

`conditions` と、`args` / `set` / `params` の値に使う。**実行しない。構文を解析して、参照を検証するだけ**（任意コードの実行はしない）。

- 参照: `$params.x`、`state名`、`query名.data` / `.isPending` / `.isError`、`source名`、ドット区切りの入れ子、`.length`
- 演算: `!` `&&` `||` `==` `!=` `<` `<=` `>` `>=`、括弧、リテラル（文字列・数値・真偽値・`null`）
- 値の指定（`args` / `set` / `params`）は、式またはリテラル。`$params.id` のように `$` を付けると、パラメータの参照を明示できる

関数呼び出し、代入、ループは**書けない**。足りなくなったら、`description` に散文で書き、式は別の `conditions` に分けて表す。

> 代替案: CEL など既存の式言語を採用する。→ 依存と学習コストが増えるため、まず小さな自前の部分集合で始め、足りなければ移行する（§9 の確認事項）。

### 4.4 イベント

| type            | 内容                                                                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `navigate`      | `targetScreenId`、`params`（値は式）。L2 の transition に対応                                                                         |
| `navigateStack` | `steps`（従来どおり）。各 step の `params` も式                                                                                       |
| `callQuery`     | `query`（`data.queries` のキー）。再取得など                                                                                          |
| `callMutation`  | `mutation`（`data.mutations` のキー）。`onSuccess` / `onError` に `refetch`（query のキー）、`set`（状態の更新）、`navigate` を書ける |
| `updateState`   | `field`（`state` の名前）、`value`（式）                                                                                              |
| `external`      | 従来どおり                                                                                                                            |
| `update`        | **v2 では非推奨。** `callMutation` / `updateState` に置き換える（info で報告）                                                        |

`guard` は、同じ画面の `conditions` のキー、または L2.guards.yaml の guard（アプリ全体の事実）を参照できる（名前空間を統合）。

### 4.5 端末のデータ源（`sources`）

位置情報・向き（コンパス）・カメラの許可など、API ではないデータ源を、型付きで宣言する。センサーを使うアプリで、L4 が「どのデータを、どこから得るか」を表せるようにするため。

```yaml
sources:
  heading:
    kind: device # device | storage | ...
    type: number
    description: 端末の向き（度）
```

`kind` の種類と、更新頻度・権限の表現は、設計を詰める必要がある（§9）。

## 5. L2 / L3 との接続（変更点）

- L3 の `action` は、L2 の transition.id、または**同じ画面の** L4 の画面内イベント（従来どおり）
- L3 の `repeatFrom` / `visibleWhen` は、L4 の `state` / `conditions` / query のキーを参照する。**v2 の画面では、存在を検証する**（v1 は検証しない）
- L2 の guard と L4 の condition の二重管理は、「`guard` の名前空間を統合」（§4.4）で解消する。L2 の guard は、画面状態を参照できない、アプリ全体の事実に限る

## 6. 検証（v2 のファイルにだけ適用。error は実装不能のものだけ）

| 検査                                                                                       | レベル                     |
| ------------------------------------------------------------------------------------------ | -------------------------- |
| 式の構文エラー                                                                             | error                      |
| 式が参照する名前が、`params` / `state` / `data` / `sources` に無い                         | error                      |
| `callMutation` / `callQuery` が、存在しない `data` のキーを参照                            | error（従来どおり）        |
| `data` の `operationId` が OpenAPI に無い                                                  | error（従来どおり）        |
| `args` が、OpenAPI のパラメータと食い違う（必須の欠落、未知の引数）                        | error                      |
| `set` / `updateState` の対象が `state` に無い。リテラルの型が `state` の型と明らかに不一致 | error                      |
| `navigate` の `targetScreenId` が L2 に無い                                                | error                      |
| `navigate` の `params` が、遷移先の L4 の `params` と食い違う（必須の欠落、未知）          | error                      |
| L3 の `repeatFrom` / `visibleWhen` が、L4 に無い名前を参照                                 | error                      |
| `description` や文字列に HTTP メソッド + パスが書かれている（`GET /…`）                    | info（構造に直すよう促す） |
| `type: unknown` / `update` イベント / 未使用の state・query・condition                     | info                       |

## 7. 移行コマンド: `mobilespec migrate`

```bash
mobilespec migrate --specs-dir specs/mobile --openapi docs/specs/openapi.bundled.yaml           # 既定: dry-run（報告のみ）
mobilespec migrate --specs-dir specs/mobile --openapi docs/specs/openapi.bundled.yaml --write   # 書き換える
```

**変換は、情報を失わない（散文はすべて `description` に残す）。決められないものは、TODO と info にする。**

| v1                                                       | v2                                                                                                                                                               |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `state: { k: "説明" }`                                   | `state: [{ name: k, type: unknown, description: "説明" }]`（型は人が決める。info に TODO の数を出す）                                                            |
| `stateData: { k: 値 }`                                   | 値から型を推定（`false` → boolean、`[]` → `[unknown]` など）。`default` に値を入れる                                                                             |
| `dataSource: { k: 'API: GET /items/{id}' }`              | OpenAPI を引き、メソッド + パスから `operationId` を特定して `data.queries.k` にする。`args` はパスパラメータから作る（`$params.<name>`）。特定できなければ TODO |
| `update` イベントで、`description` に `API: POST …`      | OpenAPI を引き、`callMutation` に変換。特定できなければ `update` のまま TODO                                                                                     |
| `conditions: { k: "説明" }`                              | `{ k: { description: "説明" } }`。説明が単純な式（`x === true`、`list.length > 0` など）なら `expr` に変換。それ以外は `expr` なし（info）                       |
| `navigate` の `params`                                   | そのまま。値は文字列リテラルとして扱う                                                                                                                           |
| 未知のキー（`bleFlow` など）                             | `x-<キー>` に改名（検証対象外、情報は残る）                                                                                                                      |
| 別の書式（型付きのリスト、トップレベルの `params` など） | v2 に合わせて変換（先行例を参考に）                                                                                                                              |

- 変換後、`check` を実行して、結果を報告する（error があれば、その内容）
- `--write` は、ファイルを書き換える。バージョン管理の下で実行する前提（差分で確認する）
- 変換の件数・TODO の件数・特定できなかった API の一覧を、最後に出力する

## 8. 実装の段階（承認後）

| 段階 | 内容                                                                            | 互換性   |
| ---- | ------------------------------------------------------------------------------- | -------- |
| 1    | スキーマ（v2 の L4）と `version: 2` の判定。v1 は従来どおり                     | 追加のみ |
| 2    | 式のパーサと、参照の検証                                                        | v2 のみ  |
| 3    | OpenAPI との引数の整合、型の導出、`navigate` の `params` の整合                 | v2 のみ  |
| 4    | `migrate`（dry-run → `--write`）                                                | 追加のみ |
| 5    | ドキュメント（構造モデル、検証モデル、LLM_SPEC）、ADR                           |          |
| 6    | 実プロジェクトの仕様で `migrate` を試験（読み取り専用の確認）。変換の精度を測る |          |
| 7    | 2.0.0 としてリリース（**タグ付けは別途承認**）                                  |          |

テスト: 各検査の正例・負例、`migrate` の変換前後の比較（架空の例）、v1 の挙動が変わらないことの回帰。

## 9. 確認したいこと（未決事項）

1. **共存（`version: 2` をファイル単位）でよいか。** 一括で切り替える案（v1 を 2.0 で削除）もあるが、利用者の CI が一斉に壊れる。推奨は共存
2. **式言語は、小さな自前の部分集合（§4.3）でよいか。** CEL などを採用する案もある。推奨は自前の部分集合から始める
3. **型の表現**（§4.2）は、これで足りるか。特に、OpenAPI の `$ref` を直接書ける点
4. **`sources`（端末のデータ源）の設計。** `kind` の種類、更新頻度・権限の表現。センサーを使うアプリのために必要だが、実プロジェクトでの先行例がない。初版では `device` / `storage` のみ、で良いか
5. **`callMutation` の `onSuccess` の表現力**（`refetch` / `set` / `navigate` のみ）で足りるか
6. L2 の guard と L4 の condition を、**名前空間の統合**で扱う案（§4.4）でよいか。別の案: L2 の guard も式で定義する
7. **v1 の削除時期**（3.0 で削除でよいか）
